## 같은 소스에서 실행한 릴리즈 시나리오

Flutter 3.50.0 stable에서 웹 13/13, Android 12/13, iOS 11/13이 통과했다. Android에서는 위젯 수명 주기 검증이 75초 제한을 넘었다. iOS에서는 실제 두 번 탭한 후 공개 콜백이 도착하지 않았고, 인라인 HTML을 다시 불러온 뒤에도 이전 JS 상태가 남았다. 같은 빌드에서 위젯 수명 주기만 다시 실행하면 Android는 통과했고 iOS의 인라인 HTML 문제는 다시 발생했다. 실행 전후 소스 지문, 파일별 해시, 플랫폼별 결과는 [실행 기록](release-scenarios.json)에 있다. 이는 해당 앱 시나리오의 결과이며 SDK 전체 계약 동등성은 미확정이다.

공식 TData 예제의 역지오코딩 요청은 동일한 좌표로 두 번 모두 HTTP 200을 받았다. 공식 예제 호스트에서 제공하는 jQuery 3.5.1이 있을 때에는 표준 콜백으로 주소가 전달됐다. 이를 뺀 환경에서는 응답 파싱 중 오류가 발생해 콜백을 받지 못했다. [SDK와 jQuery 출처](example-host-dependencies.json), [실제 콜백 관찰](tdata-reference.json). 예제 호스트와 운영 호스트는 서로 다른 JS 바이트를 제공했다. [두 배포본의 AST 후보 차이](example-production-ast-comparison.json).

## 인증 부트스트랩과 운영 CDN 확인

[공식 입력 목록](reference-inputs.json)은 URL·역할 94건과 고유 본문 84개를 묶는다. 인증 부트스트랩은 독립 요청 2회에서 1,212바이트로 일치했다. 실제 Chrome의 지도 초기화 4회에서 부트스트랩이 선택한 운영 CDN 세 곳을 모두 관찰했다. 세 CDN과 Flutter 웹 로더의 고정 호스트에서 읽은 SDK 본체와 CSS 해시는 같았다. 공식 예제 호스트의 SDK 본체는 다른 해시였다. 내용 식별자 `46b6767a…`에는 URL·역할·본문 길이·해시가 포함되며, 수집 시각이 바뀌면 별도 수집 식별자가 생성된다. 위 3,854행의 감사와 b010 플랫폼 실행은 이전 시점의 결과다. 이 확장 입력 목록으로 수행한 계약 판정은 아직 없다.

[제스처·위젯 수명 주기의 단언 검토](gesture-lifecycle-assertions.md)에는 25개 단언 그룹을 공식 SDK 계약, Flutter 고유 동작, 기대 근거가 부족한 경우로 구분했다. iOS 통합 실행은 두 번 탭 콜백에서 중단됐으므로 해당 실행에서 이후 제스처의 통과 여부를 알 수 없다. 드래그 시작과 종료 시점의 좌표가 반드시 다른지, 인라인 HTML 재로드가 주입한 문자열까지 복원하는지는 공개 문서에서 보장하지 않는다.

Flutter 웹 앱의 지도 표시 시나리오를 같은 소스에서 프로파일 모드로 실행해 통과했다. 이 실행에서 Chrome이 실제로 받은 인증 스크립트·SDK 본체·CSS, 파싱한 두 스크립트, 실행된 워커 8개의 본문 해시가 94건 입력 목록과 일치했다. [Flutter 웹 실행 증거](flutter-web-sdk-receipt.json).

별도로 서울 도심 지도에서 운영 SDK를 네 차례 실행했고, 지도와 마커 생성·교통정보·클러스터·그리기·스타일 변경 중 내려받은 외부 자산을 기록했다. 바이너리 스타일 파일 하나를 차단한 대조군은 14초 동안 지도 준비 이벤트를 보내지 않았고 화면 대부분이 회색이었다. 시간별 교통정보와 지도 타일은 렌더링 설정·글꼴·아이콘과 구분했다. [자산별 응답 해시와 차단 실험](runtime-dependencies.json.gz).

문서 의존성까지 확장한 [입력 목록](reference-inputs-doc-host.json.gz)은 앞선 94건을 포함해 128개 URL·역할과 고유 본문 118개를 고정한다. 공식 HTML 78개에서 외부 스크립트·스타일·아이콘 태그 47개의 출처를 찾았다. 대표 페이지 세 곳을 브라우저에서 열어 실제 요청과 실행을 구분했다. 문서 SDK의 워커는 운영 SDK 워커와 길이가 같았지만 해시는 달랐다. 문서에서 참조한 스크립트 세 개는 이 세 번의 실행에서는 요청되지 않았다.

Android와 iOS에서도 같은 지도 표시 시나리오가 통과했다. 플랫폼마다 WebView 문서 네 개에서 확인한 SDK 코어는 모두 1,281,499바이트에 SHA-256 `5290e0fd…`였다. Android는 세 문서의 네트워크 전송을 확인했고 한 문서는 캐시 적중이었다. iOS는 한 문서에서 네트워크 수신과 본문을 연결했고 다른 세 문서에서는 해당 페이지가 읽은 본문을 확인했다. 웹은 프로파일, 모바일은 디버그 빌드였으며 세 실행의 시나리오 파일과 소스 지문은 동일했다. [Android·iOS 실행 증거](flutter-mobile-sdk-receipt.json).

## Android 수명주기와 제스처, iOS 다중 터치

Android는 인라인 문서 재로드 후 첫 WebView 조회가 전체 30초를 소진했다. 같은 컨트롤러로 다시 읽으면 요소가 이미 표시돼 있었다. 개별 조회에 1초 기한을 둔 뒤 두 앱 프로세스에서 시나리오가 통과했다. 별도로 지도 해제 중 리스너 배열을 찾지 못한 예외가 6회에서 0회로 줄었다. 지도 컨트롤은 위젯 갱신·개별 토글 후 개수가 기대값과 일치했고, 위젯을 해제하면 엔진에서도 제거됐다. [재로드·해제 측정](android-widget-lifecycle-retry.json.gz) · [컨트롤 개수·제거 측정](android-control-removal.json.gz)

Android에서 더블 탭 줌이 끝난 뒤 실제 터치로 길게 누르면 세 번 모두 401~403ms에 공식 SDK와 Dart 콜백이 도착했다. 줌 도중 시작한 세 번은 콜백이 없었다. Flutter 없이 띄운 공식 지도에서도 같은 차이를 관찰했다. [Android 실제 터치 기록](android-native-long-press.json.gz)

iOS 수정 후보에서는 중앙·비중앙 더블 탭의 좌표가 SDK 변환값과 일치했다. 탭 뒤 드래그, 길게 누른 뒤 단일 탭의 허위 더블 탭은 각각 1회에서 0회로 줄었다. 29포인트 떨어진 두 손가락을 동시에 대고 차례로 떼면 허위 더블 탭이 1회 남았다. 이 기기의 정식 시나리오는 더블 탭 이후 줌이 16에 머물러 중단됐다. [iOS 실제 터치·좌표·줌 기록](ios-multitouch.json.gz)

Flutter 3.50.0 stable에서 같은 13개 시나리오를 웹·Android·iOS에서 실행해 39건이 통과했다. 세 프로세스의 종료 코드는 0이었다. 준비된 빌드 입력 145개의 실행 전후 SHA-256을 대조했고, 세 플랫폼의 전체 지문은 모두 `8c6855811b7e851b4728963bbda0514434d658fcc898a36ade753f7d3c31fddf`였다. 이 결과에는 지도 제스처와 위젯 수명주기가 포함된다. 커밋 `a45ca8a`의 제품 코드와 통합 시나리오는 통과한 입력에서 복원했다. 비중앙 탭은 실제 입력 전에 공식 SDK가 계산한 좌표와 Dart 콜백을 화면 2픽셀 허용 오차로 대조했다. iOS에서 길게 누른 직후 16ms 만에 시작한 드래그는 Flutter에 도착했지만 WKWebView가 받지 못했다. 통과한 독립 드래그 시나리오는 두 동작 사이에 850ms를 둔다. Android에서 길게 누른 후 같은 위치를 164ms 뒤 탭하면 공식 SDK가 ContextMenu와 DoubleClick을 모두 발행한 경우도 기록했다. [iOS 실제 터치 간격 대조](ios-gesture-spacing.json.gz)

## 좌표 변환표의 동적 키

공식 SDK 원본을 Chromium에서 실행한 뒤 좌표 변환 객체의 생성자 실행 직후에 멈춰 배열과 열거형의 값을 읽었다. 디버거가 받은 스크립트의 SHA-256은 고정한 코어와 일치했다. 추출기가 동적 속성 쓰기로 보고한 54곳 중 39곳은 이 생성자가 내부 배열 7개를 초기화하는 문장이었고, 39곳 모두 숫자 인덱스와 실제 배열 값이 원문의 대입과 일치했다. 공개 변환 메서드 자체의 좌표 변환 정확도는 이 측정 범위에 포함되지 않는다. [원문 위치·인덱스·실제 값](projection-initialization.json.gz)

## 호출자가 정하는 객체 속성과 XML 네임스페이스

고정한 SDK의 `base.Object.addProperty`에 서로 다른 이름과 값을 넣었다. 첫 수신 객체에 열거되지 않는 getter·setter가 생겼고, 속성에 새 값을 대입하자 등록한 콜백이 1회 발생했다. 두 번째 객체에는 같은 이름의 자체 속성이 생기지 않았다. XML 쪽에서는 생성자에 전달한 접두사와 URI, 그리고 `setNamespace`로 추가한 두 쌍이 정방향·역방향 사전에 저장됐다. 접두사 이름이 XML 객체의 자체 속성으로 생기지는 않았다.

디버거가 다섯 소스 위치에서 각각 두 번 멈춘 기록과 실제 저장값을 보관했다. 이름은 호출자가 정하므로 이 관찰로 가능한 키 목록을 닫지 않았다. [입력·속성 설명자·중단점·실제 값](object-and-xml-dynamic-keys.json.gz)
